# 기획 대화 (planning)

무엇을 만들지 사용자와 **말로 먼저 정한 뒤에** 스펙을 쓴다. 스펙이 서면 `chageun:spec-gate` 가 받는다.

**간단해 보여도 건너뛰지 않는다.** "이건 뻔하니 바로 만들자"는 판단을 이 스킬 안에서 내리지 않는다 (발동 조건에 걸렸으면 절차를 돈다 - 양은 줄이되 칸은 안 뺀다). 짧은 요청일수록 사용자 머릿속에만 있는 전제가 많다.

**기획 대화가 끝나기 전에 코드로 넘어가지 않는다.** 절이 다 합의되고 스펙이 서기 전에는 구현 스킬로 새지 않는다.

안전 규칙은 코어가 단일 원본이다: `멈춤 규칙` · `실제 구동 검증` · `보안·승인 위생` · `작업 규모 스위치`. 여기서 다시 정의하지 않는다.

## 0. 계획 모드로 들어간다 (구현 잠그기)

첫 응답에서 **`EnterPlanMode`** 를 부른다. 합의 전에 파일이 바뀌는 길을 기계로 막는 자리다(말로 하는 다짐이 아니다).
- 모드 안에서 하는 것: 읽기·검색·질문·선택지 제시, 그리고 6번의 스펙 파일 쓰기.
- 순서는 `절 합의 → 스펙 파일 → ExitPlanMode 승인 → 확인 게이트(🙋)` 다. 구현은 그 승인에 넣지 않는다(계획 검증이 아직 안 끝났다).
- 회복로: **모드가 스펙 파일 쓰기를 막으면 그 자리에서 `ExitPlanMode` 승인을 먼저 받고 쓴다.** 다른 길을 즉흥으로 만들지 않는다(모드 안 쓰기가 되는 것을 봤지만 표본이 1대 1회이고, 권한 확인을 켠 환경에서는 막힐 수 있다).
- **"이 계획 괜찮나요?"를 `AskUserQuestion` 으로 묻지 않는다** - 그건 `ExitPlanMode` 가 하는 일이다(절 단위 확인은 5번에서 이미 받는다).

## 1. 지금 무엇이 있나 (읽기)

- `docs/feature-spec.md` · `docs/ia-structure.md` 를 먼저 읽는다(없으면 "제품 지도부터 만들까요?" 한 줄). 상세는 `chageun:product-map`.
- 관련 파일·최근 커밋을 훑는다. 분량이 있으면 `Explore` 에이전트에 읽기만 위임한다(위임 규율은 `chageun:routing`).
- 낯선 도메인이거나 객관 신호(feature-spec 없음 · 그 도메인 첫 기능 · 규제·결제·개인정보)가 있으면 **blind spot pass** 를 먼저 한다(상세: `chageun:spec-gate`).

## 2. 너무 크면 먼저 쪼갠다

요청이 서로 독립인 덩어리 여럿(예: 채팅 + 결제 + 통계)이면 **세부 질문을 시작하기 전에** 그 사실을 알린다. 큰 요청의 세부를 다듬는 데 질문을 쓰면 나중에 통째로 버린다.
- 쪼갠 덩어리 목록과 순서를 `AskUserQuestion` **한 문항**으로 확인받는다(선택지 = 어느 것부터 만들까).
- 고른 덩어리 하나만 이 절차로 끝까지 간다. 나머지는 `TaskCreate` 로 남겨 잊히지 않게 한다. 덩어리마다 스펙·계획·구현이 따로 돈다.

## 3. 갈림길을 하나씩 묻는다

**`AskUserQuestion` 으로 낼 것**(닫힌 갈림길): 선택지가 2~4개로 정리되는 결정 - 범위(v1에 넣나 빼나) · A안/B안 · 데이터를 어디에 두나 · 공개 범위 · 무엇을 안 할 것인가.
- **한 문항이 기본.** 서로 얽혀 따로 답할 수 없는 것만 최대 2문항을 한 번에 낸다. 비개발자는 문항이 쌓이면 뜻을 잃는다.
- 선택지마다 **득실 한 줄**(`description`)을 붙이고 **추천을 맨 앞에** 둔다. 왜 그것인지 한 줄.
- 화면·문구·표처럼 **보여야 이해되는 것**은 선택지에 미리보기(목업 텍스트·표·예시 값)를 함께 넣는다. 말로만 설명하지 않는다. 시각 미지가 크면 HTML 목업으로 올린다(상세: `chageun:spec-gate`).
- 선택지가 답을 가둘 것 같으면 "그 밖"에 직접 적어도 된다고 문항에 한 줄 적는다.

**말로 물을 것**(열린 질문): "이걸 왜 하고 싶으신가요" · "지금은 어떻게 하고 계신가요" · "다 되면 무엇으로 확인하실 건가요". 선택지로 가두면 목적이 왜곡된다.

**묻지 말 것:** 사용자가 이미 말한 것, 코드·문서를 읽으면 알 수 있는 것, 뒤 게이트(plan-validator·pr-reviewer)가 잡을 기술 위험.

제품 판단(기능·입력칸을 없앨까 남길까)이면 **여쭙기 전에** 타사 관행을 조사해 선택지 근거로 붙인다(`chageun:referencing`).

## 4. 2~3안 + 득실 + 추천

방식이 갈리면 안을 2~3개 만든다. 가장 단순한 안을 먼저 놓고(코어 `최소 구현 우선`), 안마다 (가) 뭐가 좋고 (나) 뭘 포기하고 (다) 되돌리기가 얼마나 비싼지를 한 줄씩 적는다. 추천을 먼저 말하고 이유를 붙인다.
`AskUserQuestion` 한 문항 = 안 2~3개 + "다 아니다". 필요 없는 기능은 모든 안에서 먼저 뺀다.

## 5. 절 단위로 합의 (설계 승인)

합의한 것을 **절 단위로** 낸다: (가) 목적·성공 기준 (나) 범위와 안 하는 것 (다) 화면·흐름 (라) 데이터·규칙 (어디까지가 한 덩어리인가) (마) 잘못되면.
- 절 하나를 낸 뒤 다음 절로 가기 전에 확인받는다. 고칠 게 나오면 그 절만 다시 낸다.
- 절 길이는 복잡도에 맞춘다(간단하면 두세 줄).
- 확인은 **`AskUserQuestion` 한 문항**(이대로 / 고칠 데 있다 / 앞 절로 돌아가자)으로 낸다. 열린 "괜찮으세요?"는 도장만 찍히고 지나간다.
- 계산·규칙(돈·재고·날짜·권한)이 있으면 여기서 "예시로 확인"도 함께 받는다(상세: `chageun:spec-gate`).

## 6. 스펙 파일로 적는다

절 전부가 합의되면 스펙을 파일로 적는다. 갈래는 둘뿐이다: (가) 계획 모드 안에서 그대로 쓴다. (나) 모드가 스펙 파일 쓰기를 막으면 그 자리에서 `ExitPlanMode` 승인을 먼저 받고 쓴다(0번 회복로와 같은 말이다). **어느 갈래로 가든 확인 게이트(🙋)는 스펙 파일이 있는 상태에서 마지막에 돈다.** 이 순서가 사용자 뜻을 지키는 마지막 장치라, (나)로 갔다고 게이트를 앞당기거나 건너뛰지 않는다.
- 자리: `docs/specs/YYYY-MM-DD-<주제>-design.md`. 사용자가 정해 둔 자리가 있으면 그것이 이긴다. 폴더가 없으면 이 스킬이 만든다.
- 구현 계획서는 뒤에서 `docs/plans/YYYY-MM-DD-<주제>.md` 에 쓴다. **그 경로여야** "계획을 검증 없이 구현" 리마인더가 켜진다.
- 3층(한눈에 / 🙋 확인 필요 / 본문)으로 쓴다. 층 정의와 🙋 판정은 `chageun:spec-gate` 가 단일 원본이다.
- 커밋은 저장소 관례를 따른다. `docs/` 가 무시 대상인 저장소에서는 커밋하지 않는다(확인하고 결정한다).

## 7. 스펙 자기점검 (쓴 직후 · 게이트 전)

쓴 스펙을 새 눈으로 한 번 훑고 **그 자리에서 고친다**(다시 훑지는 않는다).
1. **빈칸:** TBD·TODO·"나중에 정함"이 남았나 → 채우거나 🙋로 올린다.
2. **모순:** 절끼리 어긋나나(화면은 있는데 담을 데가 없다 등).
3. **모호:** 두 가지로 읽히는 문장이 있나 → 하나로 못박는다.
4. **범위:** 계획 하나로 갈 만한가, 아니면 2번(쪼개기)으로 돌아가야 하나.

## 8. 넘긴다

스펙이 서면 `chageun:spec-gate`(한눈에 + 🙋) → 구현 계획은 내장 `Plan` 에이전트 → plan-validator → 구현(위임 규율은 `chageun:routing`).
**`Plan` 에이전트는 사용자에게 질문을 못 띄우고 파일도 못 쓴다.** 그러니 사용자 결정은 이 스킬에서 **다 끝내고** 넘기고, 그 에이전트가 낸 계획서는 메인이 위 `docs/plans/` 경로에 쓴다. 넘긴 뒤 새 갈림길이 나오면 그 에이전트가 정하게 두지 않고, 이 스킬로 돌아와 묻는다.
**`Plan` 에이전트가 없는 판이면 메인이 최상위 모델로 계획서를 직접 쓴다. 흐름을 멈추지 않는다.**
계획서는 작업 단위(Task N + Files + 단계)로 쪼개고 단계는 `- [ ]` 로 적는다.
**계획서도 스펙과 같이 낸다:** 맨 위에 `한눈에` + `🙋 확인 필요` 를 얹고 **대화창에는 그 둘만 보여 준다**(전문은 파일 링크). 계획서에는 3층 규칙이 따로 안 걸려 있어, 그냥 내면 비개발자가 못 읽는 문서를 승인하게 된다.
계획서에 빈 칸이 남았으면 **내가 메우지 않고 선택지로 묻는다**(`AskUserQuestion`). 계획 모드는 파일 변경을 막아 주는 자물쇠일 뿐 질문을 시켜 주지 않는다.
작업 시작 카드는 코어 규칙대로 **구현 착수 앞**에 낸다(기획 대화에는 안 낸다).
